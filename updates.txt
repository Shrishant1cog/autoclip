================================================================================
1. WHAT THE PROJECT IS
================================================================================

AutoClip is an open-source, local-first AI video clipper [RECORD: README.md].

Long video in -> ranked, caption-burned, speaker-tracked 9:16 clips out, and
optionally onto YouTube or Instagram. The loop it ships is:

    ingest -> transcribe -> find the moments worth keeping (a language model)
           -> reframe to vertical, tracking whoever is speaking
           -> burn in animated captions -> validate the render -> publish

Three ways to run it [RECORD: README.md]:

  - Fully local: Whisper + Ollama. Nothing leaves the machine, no API costs.
  - Bring your own key: 16 LLM providers, with multi-key pools and automatic
    fallback between them.
  - External speech: an ElevenLabs key switches transcription to Scribe.

Privacy shape, as documented: only transcript TEXT is ever sent to a text
provider - never video or audio. Audio reaches ElevenLabs only when external
transcription or voiceover is enabled AND the external-processing consent has
been granted. Every external transfer is listed in Settings -> External
processing with its destination class and its outcome [RECORD: README.md].

Licence: MIT. Version: 0.1.0.dev0 [MEASURED: autoclip.__version__].
Pre-1.0: tagging v0.1.0 is still gated on K1 (the reframe golden set).

3. MILESTONES - WHAT WAS BUILT
================================================================================

8 of 8 specification milestones are complete, plus five post-release increments
[RECORD: FINAL_UPGRADE_REPORT.md sections 1-2].

M0   Audit and baseline
     A 20-section audit, a 129-row feature coverage matrix, a 14-path egress
     inventory, a security and SSRF audit, CI baseline evidence, a performance
     baseline, an external-constraints register, and a full search record for
     the missing original sources. An independent adversarial review returned
     11 corrections, all applied before the milestone was recorded complete.

M0.5 Security and consent
     A single egress gateway (security/egress.py) and a URL policy
     (security/urlpolicy.py) that every external transfer passes through -
     including the ones that already existed (ElevenLabs STT/TTS, all four LLM
     adapters, yt-dlp, FFmpeg, the MediaPipe model download, the YouTube
     trending chart, the YouTube upload). Destinations are classified as
     loopback, private or public; redirects are re-classified hop by hop; DNS
     is resolved twice to defeat rebinding; IPv4, IPv6 and IPv4-mapped forms are
     all classified; FFmpeg runs with -protocol_whitelist file,pipe; yt-dlp runs
     with its proxy disabled. The 26 SSRF tests pre-registered as
     xfail(strict=True) became ordinary passing tests and every marker was
     deleted. The tree now has ZERO xfail markers.

M1   Music intelligence and speech-aware ducking
     A music library that indexes the user's files and never copies, moves or
     deletes them; local deterministic analysis (spectral flux, autocorrelation
     BPM, RMS energy, ebur128 LUFS, heuristic mood); a licensing model with five
     states where unknown blocks the export and where "verified" deliberately
     cannot be set by a user; and a single shared speech timeline that drives
     both the ducking and the webcam layout - there is no second detector in
     the tree. The ducking boundary is exact: a 349 ms gap merges, a 350 ms gap
     does not, computed on millisecond timestamps rather than 30 ms frames.

M2   Webcam detection and intelligent layouts
     A webcam region detected as a persistent, stable cluster of faces, scored
     on support, stability, cut-stability and persistence, with adaptive
     sampling that raises the frame rate where cuts are dense. Below a
     confidence floor of 0.35 the result is gameplay-only, not a guess. The
     stacked layout is a true split - gameplay scaled to its slot over a blurred
     background, the webcam cut from the same source in parallel trims so it
     stays in sync with the crop-path concat. The user's choice is stored
     separately from what the detector found, and the detector never overwrites
     a choice.

M3   Creative intelligence
     A structured creative plan validated in full before use - a malformed plan
     is rejected, not patched - with one repair retry and then a deterministic
     fallback whose reason is recorded. An AI call budget of 1 planning call +
     1 repair + <=1 music call per clip, capped at max_clips (12 calls at the
     default of 10), with the counters persisted in job_ai_budget so a retried
     job does not get a fresh allowance. Ten named objective diagnostics - no
     score, no rating, no invented quality figure. The model's own 0-100 clip
     score is labelled a "creative suggestion" everywhere it appears.

M4a  YouTube publishing hardening
     Per-account OAuth (the Google account owns the credential and the channel;
     the token is filed under youtube_refresh#<account_id>; an invalid_grant
     marks only that account for reconnection). An explicit publishing policy -
     madeForKids is a tri-state whose UNDECIDED state refuses the upload, and
     the privacy asked for is read back after the fact so the UI can say
     "uploaded, private" rather than "on YouTube". A resumable upload with a
     chunked session, a quota ledger and a bounded backoff. Reconciliation that
     grades its evidence - confirmed, evidence, not-uploaded, unknown - and
     never turns an ambiguous result into a second upload. A routing decision
     that explains itself, recorded whole at enqueue time so the record
     survives a later rule edit.

M4b  Instagram publishing hardening
     The current official API - the Instagram Platform Content Publishing API,
     Graph v27.0 - evaluated against Meta's own documentation, read on
     2026-11-20, with the URL for every figure. Meta supports three setups, not
     two, and they are not interchangeable: two can take a local file and one
     cannot, so AutoClip refuses a local file on the Instagram Login setup
     rather than routing it somewhere else. Meta's error table is transcribed
     into the code and each code maps to one decision. The publishing limit is
     read from the API because Meta's own documents contradict each other (100
     in one place, 50 in two others). Instagram runs on its own worker and its
     own tables, so an Instagram failure cannot cancel a YouTube upload and the
     reverse is also true. Two real export bugs were found by measuring the
     file rather than by reading the documentation: ffmpeg writes an MP4 edit
     list by default and Meta documents that a Reel must carry none, and the
     audio measured 146.4 kbps against Meta's 128 kbps limit.

M5   Audit and release - this report and its companions.

M5.1 M5.2 M5.3 M5.4 M5.5
     Post-release increments on the same branch. M5.1-M5.4 closed defects and
     widened the evidence; M5.5 added product surface (section 5 below).

6. CI - THE RUN HISTORY AND THE OUTAGE
================================================================================

43 workflow runs on this branch - the numbers are the repository's own, so the
newest is run 46 and runs 1, 2 and 3 are on main. The regression report's table
records 42 of them (runs 4 to 45); run 46 is the one it leaves out, for the
reason the table itself gives [RECORD: M5-REGRESSION-REPORT.md, "Why this table
stops here"]. Five were cancelled by a newer push (runs 6, 14, 18, 21, 32) - a
cancellation, not a failure. THREE failed, and all three were real defects,
diagnosed and fixed rather than explained away:

    run 19  a test wrote to the owner's real OS keyring. On Linux there is no
            keyring backend, so the token was never stored and the assertion
            could not hold - the test passed on Windows and macOS BECAUSE those
            machines had a real keyring to write to.
            Fixed by 94c6d9c, an autouse isolated_keyring fixture, so no test
            in the suite can reach the owner's credential store.

    run 20  the Ubuntu leg failed at "Verify ffmpeg can burn subtitles". The
            check piped the ffmpeg filter list into grep -q; grep -q exits at
            the match, the producer gets SIGPIPE, and GitHub's set -o pipefail
            turns that into a failed step. The job log shows "printf: Broken
            pipe" and then the ass filter listed on the very next line.
            Corrected, not removed: the check now matches with bash's own
            pattern matching and never pipes, and a build genuinely without the
            filter still fails it.

    run 44  the Windows leg failed at the same step, saying the build had no
            ass filter. THERE WAS NO BUILD. Chocolatey's METADATA endpoint
            (/api/v2/Packages(Id='ffmpeg-full',Version='9.1.0')) was
            unreachable - 504 on one attempt, 503 on the next - so
            "choco install ffmpeg-full" installed NOTHING and still EXITED 0,
            and the install step reported success. The next step then looked
            for the filter in a program that was never installed, and named the
            wrong cause. The job failed before any test ran. The job was
            re-run nine times - ten attempts in all - and every one failed for
            the same reason.
            Diagnosis: the same endpoint was measured timing out FROM THIS
            MACHINE in the same minutes (three requests, three 60-second
            timeouts), while the PACKAGE URL on the same host
            (/api/v2/package/ffmpeg-full/9.1.0) answered 200 throughout. So
            the outage was not the runner's, and it was not the whole of
            Chocolatey's service - the metadata endpoint is one path, the
            package is another path on the same host.

THE FIX  (commit 2e0568d)
    .github/workflows/ci.yml's Windows install step now runs
    scripts/install_ffmpeg_windows.py. Chocolatey is still tried FIRST,
    exactly as before - the ordinary case is unchanged. Only if that produced
    no ffmpeg does the script fall back to Chocolatey's own package URL. The
    package carries the build inside itself, so the fallback needs no metadata
    endpoint, no second host and no new dependency: the same package, the same
    version, the same binaries. If neither path works, the step FAILS and says
    which one failed and why, instead of leaving the next step to guess.
    Proved locally through the script's own functions: the package downloaded
    (75,480,795 bytes), unpacked, and the ffmpeg it produced is
    9.1-full_build-www.gyan.dev WITH the ass filter.
    Guarded by 6 tests in tests/test_ci_ffmpeg_install.py, which fail on the
    pre-fix workflow.

36 PRODUCT defects, all found by running the application or its gates - not by
reading the code - and every one is now guarded by a test that was observed
failing against the pre-fix code. Plus 2 defects in the CI workflow itself.

    M5.1   1   defect 4
    M5.2   4   defects 5-8

    M5.4   9   defects 14-22
    M5.5  14   defects 23-36

    total 36   product defects, running count twenty-two -> thirty-six

Plus 2 in the CI itself: the broken-pipe caption check (run 20) and the
missing-ffmpeg install (run 44).

THE M5.5 FOURTEEN, one line each [RECORD: M5-APPLICATION-TESTING.md section
M5.5 and the defect table there]

    23  the face detector could not see the streamer at all - MediaPipe scales
        its input to about 128 px on the short side, so a 120 px face in a
        1920 px frame was smaller than one pixel of what it looked at. Over
        2,100 s of the reference video it found 0 faces. Fixed by tiling the
        frame (640 px tiles, 15 % overlap): 56 observations after.
    24  the tiles were read with the wrong strides - a tile cut out of a frame
        is a non-contiguous view, and MediaPipe read it as if it were
        contiguous, so every tiled frame came back with zero faces. Fixed by
        copying each tile with np.ascontiguousarray.
    25  the edge search looked in the wrong place - the horizontal edges were
        searched in a narrow band around the face rather than over the columns
        the box occupies, so a bright game-menu panel won the vote. On the
        same 30 s the detector now finds all four edges:
        x=1274, w=638, y=9, h=426.
    26  the first frame of a clip was read from before the clip began (a
        negative clip-relative timestamp). Fixed by clamping at zero.
    27  the webcam spilled out of its own 40 % strip. Fixed by _fit_in_strip,
        which fits it inside the strip on both axes at once.
    28  the gameplay crop did not keep clear of the webcam, so the streamer
        was shown twice. Fixed by ReframeConfig.avoid plus a final _keep_clear
        pass over the finished plan.
    29  the progress page lost the video's title the moment the event stream
        opened - the server's snapshot carried the job but not its source, and
        the client replaced what it had fetched with what the stream sent.
        Fixed: the snapshot carries the source and the client MERGES.
    30  the webcam's path grew an ffmpeg expression past Windows' own
        32,767-character limit - 600 boxes became a 50,019-character filter
        graph. Fixed by thinning the path to at most 48 keyframes.
    31  the detector was asked for the stretches in the WRONG ORDER - the
        clips come in rank order and rank is not position, so it asked the
        decoder to seek backwards; the decoder refused with "Input timestamp
        must be monotonically increasing", the webcam was never found, and
        every clip was rendered as plain gameplay. Fixed by walking the source
        in source order; on the same source the detector now finds the webcam
        at 98 % confidence.
    32  a saved crop plan was reused after the layout had changed - it was
        cached under the clip's name alone, with nothing saying what it was
        made for. Fixed by a fingerprint of the settings it was built for.
    33  a detection that could not RUN was kept as a final answer - the report
        recorded why the webcam was not found, and a report with a reason was
        reused as-is. Fixed: a report says whether the detection failed or
        simply found nothing, and only a real answer is reused.
    34  a re-export would have stretched a plan made for another shape - found
        while fixing 32 by reading the path rather than by running it. Fixed:
        a saved plan is reused only when its own shape is the shape being
        exported.
    35  the saved webcam report was never reused, because the windows never
        matched exactly - the report rounds them to 3 dp while a clip's end
        time is 1303.9599999999998, so every retry paid for the detection
        again (seventeen minutes on this source). Fixed: the comparison is
        tolerant to 0.01 s.
    36  the speech-emphasis zoom broke the render - ffmpeg evaluates a scale
        filter's w and h ONCE, at init, so a per-frame expression in them is
        refused ("Expressions with frame variables 'n', 't', 'pos' are not
        valid in init eval_mode"), and every clip with a moving webcam failed
        to render. Fixed by evaluating the scale per frame (eval=frame) with a
        centred crop evaluated the same way.

The two that would have shipped without this increment are 31 (the ordering -
every clip would have come out as plain gameplay) and 36 (the per-frame zoom -
every moving-webcam clip would have failed to render).

ONE FINDING THAT IS NOT A DEFECT, because nothing the product promises was
broken: the same source, run twice, gave two different transcripts from
byte-identical media. faster-whisper's confidence check fails on hard passages
and every fallback pass above zero samples from an unseeded generator
(1.2.1 has no seed argument). It is measured in AT-G-17, the fix was verified
against the real audio (seeding CTranslate2's generator made two decodes
identical), and it is recorded as K32 / R8 rather than presented as a pass.
It is NOT applied, because it changes the transcript the acceptance evidence
was gathered on, and the evidence would then no longer describe the shipped
code; it needs its own acceptance run.

9. KNOWN LIMITATIONS
================================================================================

PRODUCT (K)
    K1   the reframe golden set is unverified - no fixed three-video set has
         been checked for jitter, cut-off faces, or the speaker being on screen
         >=95 % of speaking time. THIS IS THE GATE FOR v0.1.0.
    K2   the original requirements and 7 visual references are missing; the
         visual design could not be checked against them.
    K3   the first face-detection model download still happens at first use,
         with no pre-flight check at job start. An offline machine fails inside
         the pipeline; the error names the file and its path.
    K4   AutoClip does not take its own database backup before migrating. The
         migrations are additive and transactional, so they do not destroy
         data - but a copy of autoclip.db before upgrading is still worth
         taking.
    K5   the Instagram confirmation is API-only - there is no confirmation
         screen, the same as YouTube's.
    K6   the professional-account requirement cannot be checked locally; the
         Graph API does not report it with the publishing permissions alone, so
         AutoClip says "unverified" rather than guessing. Meta refuses the
         publish if it is not met.
    K7   Meta's own publishing-limit documentation contradicts itself - 100 in
         one place, 50 in two others. AutoClip reads the number in force and
         hardcodes neither.
    K8   there is no emergency-stop route; a job can be cancelled or retried,
         not paused and resumed.
    K9   the "verified" music licence state cannot be reached through the API.
         By design.
    K10  a re-export from the Review page does not rebuild the webcam
         composition. The framing is right - resolution, crop and duration all
         match the requested ratio - but a stacked webcam/gameplay composition
         from the layout planner is not reconstructed. This is why the M5.5
         acceptance clips were produced by REQUEUEING the job, not by
         re-exporting it.
    K22  the complete FOUR-HOUR pipeline was not run. The ingest of the
         complete file was exercised twice at two formats, and the pipeline was
         exercised on real segments cut from that same file. Transcription
         measured at 432 s per 180 s on this four-core machine, so the full
         recording would have needed roughly 9.6 hours of transcription and
         roughly 25 hours for the whole pipeline. A complete ten-minute source
         HAS been run through every stage end to end (at M5.3).
    K23  the pipeline was exercised with local models only - a local Ollama
         model and local whisper. The hosted-LLM paths remain unverified.
    K24  the caption lifetime is one constant for every style and every
         language (captions.MAX_CAPTION_S = 2.5).
    K25  the caption bound hides the symptom rather than correcting the
         alignment - a word genuinely spoken across a long pause now leaves the
         screen early, so the words after it appear with a gap in the subtitle.
    K26  the ffmpeg command line is still built inline. ffmpeg 9.0.2 removed
         -filter_complex_script, and neither -filter_complex @file nor
         -filter_complex /file reads a file - so there is no way to move a long
         graph off the command line. The M5.3 fix keeps the graph at 0.33x of
         the limit for the shape that failed, and an over-long command is
         refused before ffmpeg runs rather than failing obscurely.
    K27  the ffmpeg-version coverage is two builds wide - 7.0.2 and 9.0.2. An
         ffmpeg older than 7, or a build with a different filter set, is not
         covered by evidence. What IS established is that the graph no longer
         depends on a newer ffmpeg's leniency, and that the structural check -
         not the ffmpeg - is what catches this class of defect now.
    K28  the provider's context window is a setting, not a measurement. The
         M5.4 default of 8,192 tokens was chosen because it is the largest that
         leaves room for the model itself on this 8.4 GB machine (the extra KV
         cache measured about 680 MB; 16,384 would have added roughly 2.7 GB).
         On a smaller machine the default is too large and must be lowered.
    K29  a local model can be slow enough to look broken - one detection call
         over an eight-minute window measured 1,993 s on this box, about 33
         minutes for one request, and the highlight stage makes two of them.
         The 3,600 s default timeout is generous enough for that, but a longer
         source on a slower CPU is not bounded by anything the product
         controls, and there is no progress message inside a single window. The
         four M5.4 detection windows fit a straight line - time ~= 165 s +
         0.089 s per prompt character - to within 2.1 %, so the difference
         BETWEEN the two M5.4 runs is explained by their prompts. The gap
         against M5.3 is not explained, and it is not machine load.
    K30  the crop-safety tolerance is a fixed 90 % keep-ratio, not a per-shot
         judgement - one constant for every shot, face size and camera. The
         worst case measured on the real source is 19 px of a 549 px face
         (3.5 %).
    K31  "the same clip" is a fixed 50 %-overlap threshold - one constant, used
         by both the pipeline and the diagnostic so they cannot disagree. A
         genuine highlight inside a longer clip's range will be removed with
         it; the higher score survives.
    K32  the transcript is not reproducible from run to run (the unseeded
         recogniser fallback, described at the end of section 8).
    K33  only the English subtitle path was measured on real audio. The
         default target (en) was run against a Hindi source and the captions
         were inspected - 5,648 words, 0 outside the Latin script. A target
         that is neither English nor the spoken language takes the
         pinned-transcription path (Whisper SPEAKING in a target language
         rather than translating into it). That path is implemented, guarded
         and reachable, and what it is worth for a given pair was NOT
         measured.
    K34  the webcam-box detector's thresholds are ONE VIDEO'S constants -
         MIN_EDGE_CONTRAST = 16, MIN_VERTICAL_COVERAGE = 0.55,
         MIN_HORIZONTAL_COVERAGE = 0.85, COVERAGE_RATIO = 0.25,
         SEARCH_FACTOR = 0.9. A different game's art direction may need
         different numbers.
    K35  the MeowPower wording is a judgement, and nobody outside this
         increment has read it. The STRUCTURE - one sentence, one number, the
         technical detail one disclosure away - is what the tests and the
         screenshots hold up; the phrasing is not evidence of anything except
         that it reads plainly to the person who wrote it.

PARTIAL

    MUS-26  Duck only the added music - the speech chain is untouched and only
            the bed is shaped; measured at M5 (speech windows differ by 0.00079
            RMS, the encoder not the ducking) and again at M5.1 (the source's
            own music comes out within 0.25 of the flat render's while the
            added bed drops by at least 6 dB). The BIT-IDENTICAL render is not
            asserted - it is not possible once the bed is mixed in, so the
            guarantee is structural plus measured, not bitwise.
    CR-01   Scene detection - shots are detected once per source and cached,
            but the detector's own per-cut confidence is discarded.
    CR-02   Visual action / intensity - a documented, reproducible measure (the
            cut rate normalised by ACTION_CUTS_PER_MINUTE = 8.0), but a proxy
            for visual action, not a model of what is on screen.
    CR-04   Multi-signal highlight detection - loudness is not a signal at all;
            visual action and reaction are inferred by the model from the
            transcript, not measured.
    CR-06   Sentence/silence/scene-aware context - the edges snap to the
            nearest sentence boundary and pull back into the silence before
            the first word, but the SCENE boundary is not part of the clip-edge
            rule.
    GOV-11  The original requirements matrix - the matrix exists and every row
            records its status, but the rows that depend on the missing
            original requirements are blocked.
    GOV-17  yt-dlp network restriction - the URL is classified before the
            fetch, a private destination is refused, proxies are disabled, and
            FFmpeg runs with -protocol_whitelist file,pipe; but yt-dlp's own
            secondary requests cannot be re-classified hop by hop. A Lane B
            controlled test is still required.

    GOV-10  The original requirements and the 7 visual references - they are

    ruff check . && ruff format --check .
    pytest -m "not slow and not golden and not e2e"
    pytest -m "slow and not golden and not e2e"
    pytest tests -q --ignore=tests/test_pipeline_e2e.py

    python scripts/make_e2e_media.py --run

THE MATRIX AND THE DOCS
    python scripts/verify_matrix_counts.py        # fails if the summary and
                                                  # the rows disagree
    (scratch helpers, not repo scripts: check_docs.py <docs_dir> <repo_root>
     and check_run_table.py <path-to-docs/M5-REGRESSION-REPORT.md>)

RUNNING THE APP
    uv venv --python 3.11 && uv pip install -e ".[dev]"
    cd frontend && npm install && npm run build && cd ..
    autoclip doctor            # checks python, ffmpeg+libass, the UI build
    autoclip serve             # http://localhost:8000
    (on Windows: start-autoclip.bat does the whole sequence)

THE EXTERNAL-SERVICE RULE
    Every external transfer passes through security/egress.py and
    security/urlpolicy.py. Keys go into the OS keyring, never a config file.
    autoclip config set-secret <provider> prompts for the value, so it stays
    out of the shell history and out of the process list.
